# V2 PostgreSQL Schema

Status: additive M3 foundation; it does not yet receive product traffic or own
authoritative data.

## Ownership and migration

`Backend/persistence-postgres` owns the server-side PostgreSQL adapter and
versioned migrations. `V001__v2_core_schema.sql` is immutable after release;
later changes use new forward migrations. Flyway stores checksums in
`chat.flyway_schema_history`, validates on every migration, and has `clean`
disabled in application code.

The V1 C++/SQLite server remains the source of truth until a later vertical
slice documents its one-way import, dual-version compatibility, traffic switch,
and rollback window. Client SQLite and IndexedDB stores remain caches/outboxes,
not server truth.

## Core tables

| Table | Durable responsibility |
| --- | --- |
| `account` | normalized login identity and password hash; never plaintext credentials |
| `device` | user-owned Web or Windows device identity and revocation state |
| `device_session` | expiring/revocable session with only a SHA-256 token digest |
| `conversation` | canonical direct/group identity and next allocatable sequence |
| `conversation_member` | server-authoritative membership, role, and read sequence |
| `direct_conversation` | one canonical, ordered account pair per direct chat |
| `message` | stable message identity, conversation sequence, idempotency key, type, and bounded payload |
| `identity_import_run` | non-secret proof and reconciled counts for each committed V1 identity apply |

UUIDs are generated by the application so inserts do not depend on a single
database-side ID generator. Database timestamps are authoritative. Only
`WEB` and `WINDOWS` are accepted device platforms, matching the product scope.

V002 adds `account.password_scheme` and `legacy_password_salt` without rewriting
V001. `ARGON2ID` rows require a self-describing Argon2id prefix and null legacy
salt. Temporary `V1_SHA256` rows require a 64-character hexadecimal digest and
1..512-character salt. Successful compatibility login replaces all three
fields with Argon2id through a compare-and-set, so a concurrent password change
cannot be overwritten.

V003 adds the append-only `identity_import_run` audit. A successful apply stores
the source fingerprint, verified backup hash/size/time, source row count, and
inserted/already-present counts in the same transaction as account inserts. It
does not store source paths, usernames, password material, or salts.

## V1 identity import boundary

The identity importer first offers a repeatable-read, no-write preview. Any
unexpected target account, deterministic UUID collision, exact-username
collision, disabled account, or field difference blocks apply. A verified apply
uses a `SERIALIZABLE` transaction and exclusive peer-import table-locking,
inserts only absent accounts, then rereads the complete target and requires an
exact reconciliation before persisting its audit row and committing. A repeated
apply creates no duplicate accounts and records a new successful run.

Apply also revalidates the live SQLite identity plan and the protected backup
artifact immediately before commit. V1 is nevertheless still authoritative;
the offline operator command has no traffic route, and source quiescence plus a
final cutover check remain required.

## Implemented ordering and idempotency

A sender transaction allocates one sequence atomically:

```sql
UPDATE chat.conversation
SET next_sequence = next_sequence + 1,
    updated_at = transaction_timestamp()
WHERE id = ?
RETURNING next_sequence - 1;
```

The PostgreSQL message adapter now executes this allocation and insert in the
same transaction. Unique constraints enforce one row
per `(conversation_id, conversation_sequence)` and one outcome per
`(sender_account_id, client_message_id)`. `payload_sha256` lets the application
distinguish an exact retry from a conflicting reuse of the idempotency key. A
concurrent loser rolls back its tentative sequence before rereading the
committed winner. PostgreSQL `transaction_timestamp()` is the authoritative
acceptance time. Enabled-account, active-membership, and active-device checks run
before append inside the transaction; the same active-member boundary protects
history.

Forward history reads at most 100 stored messages after an explicit sequence,
ordered ascending, and returns the next applied cursor, current conversation
high watermark, and `hasMore`. Deleted rows remain legal cursor gaps. The
adapter is not connected to a V2 wire command yet.

## Bounds and indexes

- identifiers are limited to 128 characters at this storage boundary and are
  also limited by protocol/application UTF-8 byte policies;
- a stored message payload is limited to 1 MiB and file bytes never belong in
  this column;
- history is indexed by conversation and descending sequence;
- memberships are indexed by account for conversation-list queries;
- active sessions are partially indexed by account and expiry.

The disposable PostgreSQL gate proves the forward-history query is eligible for
`message_conversation_history_idx` with sequential scans disabled. This is an
index-eligibility regression check, not production planner or latency evidence.

## Implemented identity/session adapter

The M3 PostgreSQL adapter now performs exact, case-sensitive username lookup to
preserve V1 semantics. Session issuance re-locks an enabled account, upserts an
active Web/Windows device by `(account_id, client_device_id)`, refuses revoked
devices, generates a 32-byte random token, and inserts only its SHA-256 digest in
one transaction. A reconnect reuses the device UUID but receives a new session
UUID and token. Resume locks the session/account/device, verifies digest, expiry,
revocation and negotiated device identity, atomically replaces the digest with a
fresh proof, extends expiry, and keeps the session UUID stable. Sequential and
concurrent reuse of the old proof is rejected. Expired-session cleanup is not
implemented yet.

## Deployment and rollback

Before migrating a database that owns traffic, operations must take and verify a
restorable `pg_dump --format=custom` backup (or a documented physical/PITR
checkpoint), record the current application and migration versions, and stop the
rollout if Flyway validation fails. Production migrations run forward only; no
automatic down migration or `clean` is allowed.

At the current additive stage, rollback means disabling/removing the unused Java
route while V1 SQLite remains authoritative. Once PostgreSQL owns a slice,
rollback must restore the pre-migration backup or use the slice-specific
expand/migrate/contract plan; simply starting an older binary is not sufficient
unless its schema compatibility was verified.

## Verification

`python3 tools/verify_m0.py --postgres` starts a disposable local PostgreSQL
cluster, migrates a clean database through V003, reruns migration as a simulated
restart,
validates checksums/table shape, and tests atomic sequence allocation plus both
unique conflict paths. It also races exact adapter submissions, proves stable
duplicate results without a consumed sequence, rejects conflicting reuse,
checks bounded cursor pages, and denies outsiders/left members. It tests identity lookup, transactional device
reuse, hashed session issuance, revoked-device denial, and account-disable race
closure. It applies all three migrations, rejects inconsistent credential shapes,
maps both V1 credential generations, and verifies one-time CAS upgrade. Session
tests cover digest rotation, sequential and concurrent replay denial, device
binding, expiry, and revocation. It also proves identity preview has no writes,
strict conflict blocking, two-generation account apply, exact post-write
reconciliation, durable proof counts, idempotent account rerun, and transaction
rollback on conflict. The evidence is environment-specific and does
not by itself qualify a production database configuration.
