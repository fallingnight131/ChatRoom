# ADR-0166: Externally Signed NSIS Uninstaller

- Status: Accepted; workflow integration completed by ADR-0167
- Date: 2026-08-12
- Owners: Release engineering and security
- Amends: ADR-0164

## Context

The direct Windows installer must not show a trusted publisher for Setup and an
unknown publisher for uninstall. NSIS normally generates `Uninstall.exe` while
compiling Setup, so signing only the client, update helper, and outer Setup
leaves the installed uninstaller unsigned. The NSIS 3.08+ external-signing flow
supports exporting that generated PE and importing it during a second compile.

ADR-0164 prohibited every `!uninstfinalize` invocation to keep signing out of
NSIS. That prohibition is too broad: a finalize command can copy generated bytes
to an external signing boundary without receiving a signing credential or
performing a private-key operation.

## Decision

- Preserve ordinary unsigned verification builds and their direct
  `WriteUninstaller` behavior.
- Require `EXPORT_UNINSTALLER` and `IMPORT_SIGNED_UNINSTALLER` to be explicit,
  mutually exclusive release-build modes.
- In export mode, emit a non-release helper Setup and use one
  `!uninstfinalize` command solely to invoke `export_windows_uninstaller.py`.
- Require that tool to accept a regular non-link PE, use the canonical
  `ChatRoom-<version>-Uninstall.exe` name, refuse overwrite, copy exact bytes
  with exclusive creation, and verify SHA-256 after writing.
- Perform Authenticode signing and timestamping outside NSIS.
- In import mode, embed the externally signed canonical file as
  `Uninstall.exe` and omit both `WriteUninstaller` and the redundant outer
  uninstaller section/pages.
- Continue prohibiting `!finalize`, signing tools, certificate selectors,
  timestamp endpoints, passwords, private keys, and tokens inside NSIS.

## Consequences

The installed uninstall entry can share the reviewed project publisher while
private-key operations remain explicit in the protected layer. Release
packaging becomes a two-pass NSIS operation and retains one standalone signed
uninstaller as reproducibility/evidence input. The protected workflow,
signature-evidence schema, and candidate schema must advance before this is a
complete release path.

## Migration and Rollback

The first migration step adds only export/import capability. A later step will
sign the fourth subject, bind it into evidence and the immutable candidate, and
prove the installed bytes match. Rollback omits both new defines and returns to
the existing unsigned verification build; it never relabels that output as a
release.
